Codex custom provider returns 404: check Responses first

A working API key or Chat Completions cURL request is not enough for Codex. Use this checklist to compare the protocol, Base URL and model ID before changing credentials.

Updated 2026-11-27 · 7 minute read · No credentials required for the checklist
Quick answer

Current Codex custom model providers support only the Responses API. If your provider exposes only /chat/completions, Codex can return 404 even when the same model works through cURL or an SDK.

1. Confirm the protocol Codex expects

The official Codex configuration reference lists responses as the only supported wire_api value for custom model providers. Changing the configuration to Chat Completions is not a supported workaround.

This explains the common split result:

  • POST /v1/chat/completions works in cURL or Python.
  • Codex requests POST /v1/responses and receives 404.
  • The API key and model may be valid; the required API surface is missing.
Do not treat every 404 as a credentials problem. First identify the effective path and protocol. Repeatedly rotating keys cannot add Responses support to a Chat-only endpoint.

2. Check base_url, wire_api and the model ID

Use the provider base URL—not a full request path. For many OpenAI-compatible providers, the base ends in /v1. Codex appends the Responses route.

model = "exact-public-model-id"
model_provider = "custom"

[model_providers.custom]
name = "Custom OpenAI-compatible"
base_url = "https://provider.example/v1"
wire_api = "responses"
env_key = "AI_API_KEY"
  1. Remove duplicated endpoint segments. Do not use a Base URL ending in /responses or /chat/completions unless the provider explicitly documents a deployment-specific route.
  2. Use the exact public model ID. A display name, alias or Azure deployment name is not automatically interchangeable with another provider's model ID.
  3. Keep the key in the environment. env_key names the environment variable; the TOML file should not contain the actual secret.

Set AI_API_KEY in the same terminal, container or service runtime that starts Codex, then restart the process after correcting it.

3. Compare one Responses request—not only Chat

If you choose to run a live request, first review the provider's price. The following minimal request may be billable. It uses a non-streaming Responses call and a small output cap:

curl "https://provider.example/v1/responses" \
  -H "Authorization: Bearer $AI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"exact-public-model-id","input":"Reply with OK only.","max_output_tokens":32,"stream":false}'

A valid response should use the Responses object structure and contain a message with an output_text part. HTTP 200 with an empty or unrelated payload is not enough.

Privacy: do not paste real keys, access tokens, prompts, response bodies or internal gateway URLs into GitHub Issues or support tickets. Share only HTTP status, public model ID, client version and a redacted route shape.

4. Read the next error correctly

Observed resultMost useful next check
404 on /responsesResponses availability, Base URL construction and exact model ID. Chat success does not resolve this.
401The key visible to the Codex process. Correct env_key, renew the credential and restart Codex.
403Model entitlements, application model pools and account approval. A URL change does not grant access.
429RPM, TPM, concurrency, usable quota and Retry-After. Avoid repeated manual and automatic retries.
200 in cURL, failure in CodexStreaming and tool behavior, extra client options and the exact response fields required by the next Codex operation.

For a clean comparison, start with one minimal Codex prompt before adding custom tools or MCP servers. Reintroduce required capabilities one at a time.

5. Know what a basic compatibility check cannot prove

A non-streaming Responses pass verifies one response contract. It does not prove streaming event compatibility, tool calling, structured output, model quality or production reliability. Test those separately in your own integration.

If the provider does not support Responses, the correct resolution is to use a provider or model that supports the client you need—not to hide the incompatibility behind an unrelated Chat configuration.

Common questions

Does Codex support Chat Completions for custom model providers?

No. Current Codex documentation lists responses as the only supported wire_api value for custom model providers. A working Chat Completions request does not prove Codex compatibility.

Should base_url include /responses?

Usually no. Enter the provider base URL, commonly ending in /v1, and let Codex construct the Responses route. Check your provider documentation for deployment-specific exceptions.

Does a successful non-streaming request prove streaming and tool support?

No. Streaming frames, tool-call fields and model behavior need separate checks in the target client. A basic response-contract pass is only a first step.
