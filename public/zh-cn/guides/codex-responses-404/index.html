Codex 自定义 Provider 返回 404：优先检查 Responses

API Key 有效或 Chat Completions 的 cURL 请求成功，并不足以保证 Codex 可用。更换凭据前，先用本清单对比协议、Base URL 和模型 ID。

更新于 2026-11-27 · 约 7 分钟 · 检查清单不需要凭据
快速结论

当前 Codex 自定义模型提供方仅支持 Responses API。如果服务商只提供 /chat/completions，即使同一模型能通过 cURL 或 SDK 调用，Codex 仍可能返回 404。

1. 确认 Codex 实际需要的协议

Codex 官方配置参考仅列出 responses 作为自定义模型提供方的 wire_api 值。把配置改成 Chat Completions 并不是受支持的解决方案。

这可以解释常见的分裂结果：

  • POST /v1/chat/completions 在 cURL 或 Python 中成功。
  • Codex 请求 POST /v1/responses 并收到 404。
  • API Key 和模型可能都有效，但客户端所需的 API 协议不存在。
不要把所有 404 都当作凭据问题。先识别实际路径和协议。反复更换 Key 不可能为仅支持 Chat 的端点增加 Responses 能力。

2. 检查 base_url、wire_api 和模型 ID

应填写服务商 Base URL，而不是完整请求路径。许多 OpenAI 兼容服务商的 Base URL 以 /v1 结尾，Codex 会继续拼接 Responses 路由。

model = "exact-public-model-id"
model_provider = "custom"

[model_providers.custom]
name = "Custom OpenAI-compatible"
base_url = "https://provider.example/v1"
wire_api = "responses"
env_key = "AI_API_KEY"
  1. 删除重复的端点片段。除非服务商明确文档说明特殊部署路由，否则 Base URL 不应以 /responses 或 /chat/completions 结尾。
  2. 使用准确的公开模型 ID。显示名称、别名或 Azure 部署名称不能直接等同于其他服务商的模型 ID。
  3. Key 只放在环境变量中。env_key 表示环境变量名称，TOML 文件不应包含真实密钥。

在启动 Codex 的同一终端、容器或服务环境中设置 AI_API_KEY，修正后重新启动进程。

3. 对比一次 Responses 请求，而不只检查 Chat

如果决定执行真实请求，请先查看服务商价格。以下最小请求可能计费，使用非流式 Responses 和较小的输出上限：

curl "https://provider.example/v1/responses" \
  -H "Authorization: Bearer $AI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"exact-public-model-id","input":"Reply with OK only.","max_output_tokens":32,"stream":false}'

有效响应应采用 Responses 对象结构，并包含带 output_text 部分的消息。只有 HTTP 200，但载荷为空或结构无关，也不能算通过。

隐私：不要把真实 Key、访问令牌、提示词、响应正文或内部网关 URL 粘贴到 GitHub Issue 或支持工单。只提供 HTTP 状态、公开模型 ID、客户端版本和脱敏后的路径结构。

4. 正确理解下一个错误

观察到的结果最有用的下一项检查
/responses 返回 404Responses 可用性、Base URL 拼接和准确模型 ID。Chat 成功不能解决此问题。
401Codex 进程实际读取的 Key。修正 env_key、更新凭据并重启 Codex。
403模型权限、应用模型池和账号审批。修改 URL 不会增加访问权限。
429RPM、TPM、并发、可用额度和 Retry-After。避免手动与自动重试叠加。
cURL 返回 200，Codex 仍失败流式与工具行为、额外客户端选项，以及 Codex 下一步操作需要的响应字段。

为了进行干净对照，先用一个最小 Codex 提示词测试，再接入自定义工具或 MCP Server。每次只恢复一项所需能力。

5. 明确基础兼容检查不能证明什么

非流式 Responses 通过只验证一次响应契约，不能证明流式事件、工具调用、结构化输出、模型质量或生产可靠性。请在真实集成中分别验证。

如果服务商不支持 Responses，正确做法是更换支持目标客户端的服务商或模型，而不是用无关的 Chat 配置掩盖不兼容。

常见问题

Codex 自定义模型提供方支持 Chat Completions 吗？

不支持。当前 Codex 文档仅列出 responses 作为自定义模型提供方的 wire_api 值。Chat Completions 请求成功不能证明 Codex 兼容。

base_url 应该包含 /responses 吗？

通常不应包含。填写通常以 /v1 结尾的服务商 Base URL，由 Codex 构造 Responses 路径。特殊部署路由以服务商文档为准。

非流式请求成功能证明支持流式和工具调用吗？

不能。流式帧、工具调用字段和模型行为需要在目标客户端中单独验证。基础响应契约通过只是第一步。
